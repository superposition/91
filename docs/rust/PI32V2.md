# Rust code on the FM-1: physical compiler proof

R02 passed on the connected FM-1 on 12 November 2026. The installed test image
`FM-1_7000302` runs the original C instrument and a Rust types/formats/planner
probe once during boot, before the audio and timer interrupts start. This is
the compiler feasibility gate; the complete Rust instrument still needs its
own hardware qualification.

The pinned route is Rust source → mrustc `5205980b25d4d15494abdb45103e59e8dc309970`
with Rust 1.90 core → generated C → vendor clang 4.0.1 (`pi32v2`, `r3`,
`fprev1`, `-ffp-contract=off`) → final-image LTO and the existing package gates.
Standard Rust 1.94.1 checks the same sources, including the 32-bit WASM target.
The target layout and the conservative read-only-static patch are checked in
under [rust/toolchain](../../rust/toolchain).

Two explicit integer annotations were necessary with mrustc: the package
product iterator starts at `0usize`, and sequencer masks use `1u32`. These are
in `5cfbf29881dd0362d7825834de45f5d3a4e2e411`. Applying that two-file patch to
`4f4e970c375f04498d8122784b07b6c72e77f2bd` gives the portable sources used
for the measured image. The immutable R01 application received only the
private probe declarations, an exclusive pre-audio boot call, and read-only
Jam command 14 returning ten little-endian words.

| Probe | Actual result |
| --- | --- |
| Phrase/bass/RNG hash, seed 4 | 3,766,679,758, equal to Rust and frozen C |
| Planner elapsed time | 652 µs |
| Non-contracted binary32 multiply/add | bits `0x00000000` |
| Callback rotate/XOR | `0xbf8e99ac` |
| Explicit pool section | address 29,830,604, zero initial byte, inside pool |
| Interior-mutable static | initial 17, returned 18 |
| Volatile timer | 13,991,536 → Rust read 13,991,552 → 13,991,554 |

The release image is 510,144 bytes. Ordinary RAM is 97,264 / 98,304 bytes;
the pool is 339,420 / 344,064 bytes. The loader is 8,095 bytes. The padded
version-3 recovery stub retains SHA-256
`baee55ed142fe1cc336099902fa544d8844ba72182abf669f15cc78fc6bee87c`.
Build checks passed for executable sections, RAM-only flash paths, register
access, size, ROM restrictions and soft-double helpers. The actual package
passed the installer fake-device suite and OTA simulated-NOR suite before
installation; its identity was verified again after the device rebooted.

Symbol/disassembly inspection found no allocator, soft-double runtime or
unwind tables. An explicit six-byte `_Unwind_Resume` compatibility entry
remains: it calls the application's audio-stop/abort handler and loops. It
cannot unwind a stack. `panic_impl` follows the same abort-only policy. These
entries are recorded in the proof rather than assumed to disappear under LTO.

Before flashing, all 176 parameters and all 30 backup-readable stored objects
were captured; every object was read twice. All 8,077 stored bytes matched
after installation. A 60.05-second USB-audio capture produced 246 telemetry
frames, with peak 4,569 and RMS 914.87 in int16 units. XRUN, late-render and
crash deltas were all zero, and shedding stayed zero. Worst observed render
was 11,246 µs against an 11,609 µs budget; maximum CPU was 80%. Observed stack
high-water marks were 6,176 bytes main and 2,184 bytes IRQ.

The retained local evidence is under
`rust-migration/goal-hardware-proof-20261112` and
`rust-migration/proof-current-instrument`; emitted C and objects are under
`fm1-rust-toolchain-proof/output-goal-current` in WSL. The
[machine-readable report](pi32v2-physical-proof.json) contains identities,
measurements and SHA-256 hashes, including the audio recording. No recovery
stub or stored object was changed.

To repeat object emission with the pinned mrustc/core bootstrap and a fresh
output directory, set `JIELI_TOOLCHAIN` and `FM1_FREESTANDING`, then run
`bash rust/toolchain/emit_probe.sh TOOLCHAIN_PROOF_DIRECTORY FRESH_OUTPUT_DIRECTORY SOURCE_REVISION`.
The checked-in probe and its tests specify the vectors. A physical test image
must retain the pre-IRQ exclusive call, the read-only command, final-image LTO,
and the existing package/stub gates. Probe success does not establish the
complete engine's atomics, multicore lifetime protocol or audio deadline.

## Reproducing the core and full bridge

The checked-in `bootstrap_core.sh` now builds a fresh core from the Rust 1.90.0
source archive, SHA-256
`cde088d57064d151b2236f4619aea4a8207e0709eb3035ddc6617d609ab7d453`.
Use a separate mrustc checkout at the pinned revision with the combined
`mrustc-pi32v2.patch` applied once. `verify_mrustc.py` checks both its revision
and its complete working-tree diff before compilation. The combined patch
includes the earlier read-only-static change; do not apply both patches.

```sh
export JIELI_TOOLCHAIN=/path/to/vendor-toolchain
bash rust/toolchain/bootstrap_core.sh /path/to/mrustc \
  /path/to/rust-src-1.90.0.tar.xz /absolute/fresh-core
bash rust/toolchain/emit_bridge.sh /path/to/mrustc /absolute/fresh-core \
  /absolute/fresh-bridge SOURCE_REVISION
```

These commands use local inputs and fresh output directories. The core output
retains its source, log, generated C, HIR metadata, vendor LTO object and hashes.
The bridge command first runs the standard Rust 1.94.1 release/no_std/WASM
check, then emits all five libraries: types, formats, engine, runtime and bridge.
Both stages retain `-ffp-contract=off`; the runtime uses the opaque hardware
atomic ABI. A fresh core and all five libraries were compiled successfully
with these scripts on 12 November. This verifies build reproducibility and
does not establish hardware runtime behavior.

## Integrated hardware test in progress

The private `FM-1_7000304` test image combines the current Rust planner,
transport, scheduling, voices, FM6, effects, worker and codecs with the C
application/HAL. Whole-image LTO passes the flash, memory, register-access and
no-soft-double gates: image **546,724 bytes**, ordinary RAM **97,976 / 98,304**,
pool **339,404 / 344,064**. The recovery stub remains unchanged. The install
package passed simulated installer and actual-package NOR tests before use.

The installer verified the new identity after restarting, but the next runtime
query found no MIDI port; Windows reported a USB device descriptor failure.
No integrated-engine audio, stack or deadline measurement was obtained.
This observation is unresolved, and the earlier compiler/atomic probe results
must not be presented as qualification of the full engine. A fresh backup of
all 30 readable saved objects was read and independently verified before this
test. Evidence is retained under `proof-rust-dsp-lto` and
`goal-hardware-proof-20261112`; the user has been asked for the physical
screen/power state before further device work.
