I.Orientation

First, a map of the names.

JieLi is the chip designer; AC79 is the system-on-chip family; PI32v2 is the CPU instruction set this FM-1 project targets. Their relationship explains the firmware, the toolchain, and the unusual disassembly.

JieLi—珠海市杰理科技股份有限公司, based in Zhuhai—designs highly integrated SoCs for Bluetooth audio, multimedia, wearables, and connected devices. Its products combine processors, radios, memory controllers, audio interfaces, and specialized accelerators. This guide concerns the AC79/AC791 platform used by this project; other JieLi families can have different processors and peripherals.

II.The system on chip

A multimedia computer with a DSP at its heart.

JieLi’s AC791 development-board documentation describes a dual-core, 32-bit DSP subsystem with hardware single-precision floating point, caches, memory-management functionality, and a broad collection of interfaces.

2 × 32DSP cores · bits per core
320MHz · advertised configuration
578KB · advertised SRAM total
ResourceVendor description
Floating pointHardware single precision.

Data cache32 KB, eight-way associative, consuming SRAM.
Memory systemMMU functionality; external flash and RAM support.
InterfacesUSB, SPI, UART, timers, GPIO, audio, camera, display, and other peripherals.

These are platform capabilities. They do not establish which package, external memory, radio connections, or operating frequency a particular FM-1 board uses. The advertised SRAM total also exceeds the memory available to application variables: caches and reserved regions consume space.

Vendor sourceAC791 hardware overview ↗

One chip, several clocks.

JieLi distinguishes the CPU/system clock, external RAM clock, high-speed bus, low-speed bus, and serial-flash clock. “320 MHz CPU” does not mean memory, USB, SPI, and instruction fetching all operate at 320 MHz. A faster core can spend more time waiting for an unchanged memory subsystem.

III.The instruction set

Reading the machine’s handwriting.

PI32v2 has its own instruction encoding and assembly language. It is a distinct target from x86, ARM, and RISC-V. Selecting one of those disassemblers cannot recover the intended instructions.

The installed JieLi tools register pi32, pi32v2, and q32s. This firmware selects:

Compiler target
-target pi32v2 -mcpu=r3 -mfprev1

The installed compiler is a vendor LLVM/Clang 4.0.1 build inside jieli-linux-toolchains-20260730.1. The package date and compiler generation are different facts. The workstation’s Windows LLVM 20.1.3 does not list these JieLi targets.

The assembly resembles statements. These are real instructions printed in JieLi’s syntax, rather than reconstructed C:

PI32v2 assembly
r0 += r1
r0 = r0 * r1 (f)
r0 = b[r0+0] (u)
if (r2 != 7) goto ...

Two small compiler experiments make the relationship concrete.

Experiment 01 · integer addition
C source
int add(int a, int b) {
    return a + b;
}
Actual disassembly
0:  10 18    r0 += r1
2:  80 00    rts
Experiment 02 · extracting a bit field
C source
unsigned bits(unsigned x) {
    return (x >> 11) & 7;
}
Actual assembly
r0 = uextra(r0, p:11, l:3)
rts

The processor extracts that field directly. Counting C operators would overestimate the instructions required.

The inspected code contains two-, four-, and six-byte instructions. Instruction boundaries matter: beginning two bytes into a longer instruction can yield plausible but incorrect output. A 32-bit processor does not imply four-byte instructions.

IV.The binary interface

The contract between functions.

The application binary interface, or ABI, is the agreement between independently compiled functions. In the simple scalar functions tested, the first four 32-bit arguments use r0–r3, additional arguments use the stack, and a 32-bit integer or float result returns in r0.

The seven-argument wrapper saved r4–r6 and rets while moving the stack arguments. Register preservation and stack layout are part of the contract.

C typeCompiler-reported size
short2 bytes
int, long, pointer, size_t4 bytes
long long8 bytes
float4 bytes
double, long double8 bytes

The target is little endian, with a 32-bit pointer model. Its LLVM data layout gives 64-bit integers and doubles four-byte ABI alignment. When sharing structures with another compiler or language, matching field types alone does not establish matching structure layout.

The interrupt boundary

The project’s wrapper saves psr, rets, reti, and r0–r3, calls the C handler, restores state, executes csync, then executes rti. Its source records that the compiler does not automatically emit the synchronization needed by this wrapper. Function ABI compatibility is only one part of interrupt correctness.

V.Numerical behaviour

Precision has a price.

AC79 has hardware float support. JieLi explicitly says that hardware does not support double; double-precision arithmetic uses software.

The local hardware note’s statement about lacking a useful FPU is misleading. The vendor documentation, project build flags, and actual generated instructions establish hardware single precision.

Vendor + projectHardware floating-point documentation ↗ · Build flags ↗

With the project’s floating-point options, multiplication, addition, and division produce hardware floating-point instructions.

Source → generated instructions
// float madd(float a, float b, float c) { return a*b+c; }
r0 = r0 * r1 (f)
r0 = r0 + r2 (f)
rts

// float divide(float a, float b) { return a/b; }
r0 = r0 / r1 (f)
rts

The multiply and add remain separate under -ffp-contract=off. This experiment does not establish every possible fused operation. A single divide instruction also does not establish its latency or throughput.

Changing the arithmetic to double precision moves the work into a software helper.

Source → generated instructions
// double dadd(double a, double b) { return a+b; }
goto __adddf3

The compiler emits a transfer to __adddf3. In an unlinked object, that destination is unresolved; the symbol and relocation identify the helper.

A literal without the f suffix can silently introduce double-precision arithmetic.

Source → generated helper calls
// float accidental_double(float x) { return x + 0.1; }
call __extendsfdf2
call __adddf3
goto __truncdfsf2

That is float-to-double conversion, software double addition, then conversion back to float. Writing 0.1f selects single precision. Likewise, sinf and sin have different argument and result precision. -Wdouble-promotion caught this example.

The compiler moved the division ahead of the condition in this expression:

Actual compiler output · simplified comments
// return x > 0.8f ? 1.0f / x : 0.0f;
r1 = r0
r0 = 0x3F800000
r0 = r0 / r1 (f)
...
iff (r1 u<= r2) {
    r0 = 0
}

A zero input can reach the divide instruction even though the C expression ultimately selects zero. The firmware explicitly disables the hardware divide-by-zero trap and documents this compiler behaviour.

IRQ initialization and floating-point trap explanation ↗

Hardware exception configuration must agree with the compiler’s floating-point execution assumptions.

Acceleration is another layer.

JieLi supplies FFT/IFFT, vector, and mathematical APIs with software, assembly, or hardware implementations. Those interfaces have their own data formats, scaling, saturation, memory-placement, and length constraints. A hardware math block does not imply that an arbitrary C loop or standard-library call automatically uses it.

VI.Placement & execution

Where the code lives changes what it can do.

Memory placement determines execution speed and whether code remains accessible at all. The current application linker script allocates these regions:

Warm-reset retained state0x01C7C020.noinit region

Project evidenceApplication linker script ↗

Most application code executes directly from memory-mapped serial flash: execute in place, or XIP. Cache hits make that efficient; misses require fetching through the serial-flash controller.

Some sections have two addresses. Their load address identifies where their initial bytes reside in the image. Their execution address identifies where those bytes must be copied before use. The project’s .ram_text, .dsp_text, .ram_hot, and .data sections are stored in flash but assigned RAM addresses. Startup must copy them correctly.

.bss and .pool reserve RAM without storing a corresponding block of zero bytes in the image. A section name is a linker convention: naming a section .text does not itself establish hardware permissions, and this script also places constants there.

Two address spaces, one image.

CPU addresses differ from physical flash offsets. The project defines:

XIP mapping
CPU XIP address = 0x02000000 + flash offset - 0x4000

flash 0x4120  →  CPU 0x02000120    // boot stub
flash 0x5000  →  CPU 0x02001000    // application body

Confusing those address spaces sends debugging and patching to the wrong location.

Project XIP mapping ↗

What happens when flash is busy?

The RAM flash driver waits for the cache/controller, disables XIP, takes ownership of the flash pins, performs operations, restores the controller, and invalidates affected cached data. Every instruction and constant needed during that interval must remain accessible.

A transitive requirement

Placing the outermost function in RAM is insufficient if it calls a flash-resident helper or reads a flash-resident table. The entire active path matters.

The driver also records that a direct XIP-to-RAM call exceeds the relevant relative-call range, so it deliberately uses an indirect call. Placement affects branch reach as well as speed.

VII.Concurrency & ownership

Two cores share more than the work.

JieLi documents two operating arrangements: an operating system scheduling work across both cores, or one core running the OS while the other performs a dedicated function.

In the dedicated-core arrangement, the vendor warns that the second core cannot freely call OS APIs, including printing functions that depend on the OS. Flash writes normally suspend CPU1 in SFC mode. Avoiding that suspension requires CPU1’s complete execution path to reside in internal or external RAM.

Vendor sourceDual-core operation ↗

This project uses a dedicated worker with a mailbox. CPU0 publishes a function, context, and request; CPU1 performs the job and publishes completion. The implementation includes synchronization, separate stacks, request validation, timeouts, and fallback when the worker is retired. Its polling loop resides in RAM.

Project evidenceCore-1 worker ↗

MechanismWhat it addresses
Compiler orderingWhether the compiler may move or remove accesses.
CPU synchronizationOrdering and visibility according to the processor’s rules.
Cache maintenanceWhether another agent sees the intended memory contents.
OwnershipWhich agent may access or reuse the storage now.

A compiler barrier does not flush a cache. A CPU synchronization instruction does not establish exclusive ownership. Disabling CPU0 interrupts does not stop CPU1 or DMA. An enable-bit readback does not necessarily prove that outstanding bus transfers have finished.

volatile alone does not provide C/C++ inter-thread synchronization. The SDK uses hardware testset and csync in its locks; the project’s experimental atomic backend combines those mechanisms with interrupt-state handling.

Project atomic backend ↗

Two cores improve performance where work overlaps usefully. Serial processing, publication, waiting, cache misses, and shared-bus contention remain on the critical path. Two 320 MHz cores cannot make one serial function execute as though it had a 640 MHz core.

VIII.Real-time audio

An instrument lives by its deadline.

The DSP declares a 44.1 kHz sample rate, and the worker describes 256-frame render chunks. That gives the system approximately 5.805 milliseconds to prepare each chunk.

At a hypothetical 320 MHz operating frequency, approximately 7,256 core clock cycles are available per audio frame. That is a clock budget, not a count of useful instructions: stalls, interrupts, bus traffic, and synchronization consume it.

The deadline, calculated.

Explore the clock budget
320 MHz
5.805 msAvailable time per block
7,256Core clock cycles per frame

256 ÷ 44,100 seconds · approximately 1.858 million core clock cycles per block.

Illustrative model. Use measured clocks and supported audio configurations for hardware analysis. Instructions, stalls, and shared-resource costs all consume this budget.

The audio HAL uses double-buffered DMA through ALNK/I²S to an external codec, with stereo 24-bit audio represented in 32-bit words. DMA consumes one buffer half while software prepares the other. A deadline miss can expose stale or unfinished output data.

Worst-case render time, interrupt latency, memory contention, and flash-operation pauses are more informative than average CPU percentage. The project’s free-running 24 MHz timer measures elapsed time independently of assumptions about instruction throughput.

IX.Startup & packaging

The journey from reset to sound.

Booting involves several components with different responsibilities. The project’s normal path is approximately:

01Chip ROMImmutable first stage
02SDK startupFlash-resident SPL
03Recovery stubApplication entry checks
04ApplicationRAM, IRQs, peripherals, DSP

The immutable ROM stage and flash-resident uboot.boot component are separate. The package builder places the SDK SPL in the flash header region. The local statement that “the bootloader lives in ROM” collapses multiple stages into one. JieLi also supplies uboot.boot variants with different update and debugging capabilities.

X.Binary inspection

A familiar tool, with an unfamiliar target.

The compiled probe is ELF32, little endian, with machine identifier 0xF1. Generic tools can parse much of the ELF container while lacking its instructions or relocation definitions. Recognizing the container does not establish correct instruction decoding.

Even the vendor disassembler needs the right CPU features. Without them, it printed the first four floating-point bytes as:

Same bytes · different decoder configuration
// Without the correct CPU features
3f e5          <unknown instruction>
02 01          tbb [r2]

// With -mcpu=r3 -mattr=+fprev1
3f e5 02 01    r0 = r0 * r1 (f)

The wrong configuration changed instruction boundaries and produced a misleading instruction. Plausible assembly is not sufficient evidence of correct decoding.

Use these commands inside WSL with the installed toolchain. Replace the example filenames with the object or ELF you want to inspect.

WSL · Bash · verified command forms
JIELI_BIN="$HOME/.jieli/toolchain/pi32v2/bin"

# Section layout
"$JIELI_BIN/objdump" -h program.elf

# Symbols, including undefined references in an object
"$JIELI_BIN/objdump" -t program.o

# Decode the tested CPU and floating-point features
"$JIELI_BIN/objdump" -d -mcpu=r3 -mattr=+fprev1 program.elf

# Instructions and relocations in an unlinked object
"$JIELI_BIN/objdump" -d -r -mcpu=r3 -mattr=+fprev1 program.o

# Restrict the address range
"$JIELI_BIN/objdump" -d -mcpu=r3 -mattr=+fprev1 \
  -start-address=0x02001000 -stop-address=0x02001080 program.elf
A command-line distinction

This old LLVM-derived objdump differs from GNU’s. The tested form -d -r works; combined -dr is rejected. Some relocation symbols displayed as Unknown even though the symbol table and generated assembly identified them. Cross-check unresolved calls before interpreting displayed destinations.

XI.Evidence & diagnosis

What the binary can—and cannot—tell you.

Keep the exact linked ELF corresponding to the running image. JieLi’s exception documentation distinguishes misaligned accesses, illegal instructions, invalid addresses, divide-by-zero, stack overflow, and watchdog resets. It also warns that memory corruption can happen before the instruction where the exception finally appears.

Vendor sourceException analysis ↗

The remaining questions require evidence beyond the sources checked here: exact FM-1 chip/package identification and live clocks; complete instruction latencies; floating-point corner behaviour such as subnormals; and precise cache-coherency guarantees between cores and DMA.

Compiler output establishes what was emitted. Silicon documentation and measurements establish how it behaves.

Use generated instructions to understand transformations and dependencies. Use the memory map to understand placement and access. Use on-device timing and fault records to establish whether the complete system meets its deadlines.
